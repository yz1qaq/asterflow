# 代码评审规范

## 流程

作者提交Draft PR→自查/测试→准备就绪→Reviewer按固定head审查→作者逐项回应并修复→复审→负责人决定合并。设计和依赖不明确时先澄清，不以风格偏好阻断正确方案。
评审记录包含head SHA、范围、关键证据和问题分级。有新提交需判断旧意见是否仍成立，更新测试，不能将旧head的“通过”套到新代码。

## 检查维度

| 维度 | 关注点 |
| --- | --- |
| 需求 | 正确场景、范围和不变量，FR/任务关联 |
| 权限/安全 | 可信actor/空间/资源，凭据/日志，Schema和实际执行约束 |
| 正确性 | nil/空值/错误cause、状态转换、消息/事件顺序 |
| 数据 | 事务/行锁/条件更新、影响行数、幂等、迁移/回滚 |
| 并发/恢复 | context、goroutine退出、租约、重试/重复消费与业务副作用 |
| 可维护性 | 接口/分层/命名、SQL/sqlc、配置、复杂度 |
| 验证 | 测试真实覆盖、关键失败场景、PG/Web/协议证据 |
| 运维 | 配置、指标/日志、部署/资源/回滚说明 |

## 问题分级

P0：密钥泄漏/数据破坏等必须立即停止；P1：功能/权限/并发等重大错误，合并前修复；P2：影响使用或维护的具体问题，通常合并前修复或明确安排；P3：建议性改进。
每条意见给文件/行号或精确段落、触发条件、影响和建议，不制造不存在的问题。作者可以用代码/测试证据解释异议；复审确认后解决讨论。

## 当前个人仓库的实际限制

PR作者不能批准自己的PR。当前GitHub独立批准人数设为0，要求PR+docs检查+解决讨论；这不等于已有另一名人类审批。AI可以使用当前账号提交明确标注的COMMENT review，但不能伪装独立Approve。
引入另一名真实协作者并获得授权后，再将独立批准人数改为1，按需要启用Code Owner。当前不要求作者给自己发Review request。

官方说明：[审查PR](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)。实际保护配置见[治理记录](REPOSITORY-GOVERNANCE.md)。
