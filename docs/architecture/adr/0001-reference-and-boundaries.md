# ADR-0001：技术基线与工程边界

日期2026-11-14，状态：已采纳，负责人已合并设计PR #3。

## 背景

AsterFlow需要完整交付PRD，保留明确来源并实现可验证的模块边界。参考版本固定，避免后续上游变化导致需求漂移。

## 决策

1. 冻结来源仓库Q1mi/kbot的baed6c354e1966cdae7bc5328e771dc50ae6c70b:kbot-final；全部已实现模块进入追踪表。上游未实现演进项另列。
2. 产品名/仓库asterflow，平台Go module计划github.com/yz1qaq/asterflow，CLI计划asterctl，配置前缀计划ASTERFLOW_。对外资源/JSON/事件沿基线语义，改名映射在对应任务明确，不全局字符串替换破坏协议。
3. 平台采用模块化Go+独立Server/Worker/Runner；业务系统在business_systems/crossborder与insurance独立目录/进程/PG库。参考projects到目标目录按映射对齐；本轮不复制业务实现。
4. PG为事实源，Redis为缓存/队列，MinIO归档/导出，观测栈独立。模块通过服务接口/不可变配置与协议协作。
5. 完整范围不以迭代次数限定，按Epic/任务/PR逐项验收；不能完成基础子集后把其余模块移为无排期选修。
6. 默认人类后端负责人写生产Go/SQL，助手提供前端/测试/运维/文档；每轮只推进明确任务。外部付费调用另获授权。
7. 使用Issue/PR/CI/Review，单账号AI COMMENT与真正独立Approve分开；设计PR待负责人确认。

## 备选与影响

直接导入完整源码能快速运行但无法建立本仓库从零任务与评审证据；全量微服务增加分布式复杂度且偏离基线，因此选模块化平台增量交付。
选择PG业务适配会增加业务迁移/Store工作，换取持久化和独立运行；要求保存相同业务行为并记录与参考内存实现差异。
公开个人仓库可以使用当前账号的分支保护，但不等于组织身份/真实多人审批。协作规则记录真实限制。

## 验证

本ADR由负责人在设计PR审阅。后续每个Epic的接口/数据/行为测试及最终来源清单核对验证落地；批准本ADR不代表功能已实现。
